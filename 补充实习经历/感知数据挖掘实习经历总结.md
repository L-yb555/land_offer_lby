## 二、业务背景与平台定位

感知数据挖掘平台是自动驾驶数据闭环中的一环。上游对接车载摄像头采集的图像/视频数据，下游输出 taggers / 标签，最终用于：

- 感知数据自动化标注
- Corner Case / 边缘场景挖掘
- 数据筛选和检索
- 标签库建设
- 后续模型训练、评估与数据闭环迭代

图片中提到两条并列的挖掘技术路线：

- 图搜：基于特征相似度检索。
- VLM 刷库：基于视觉语言模型的语义理解，对图片或视频帧进行语义判断、属性识别和结构化打标。

可以理解为：图搜更偏相似样本召回，VLM 刷库更偏语义理解和开放场景判断。

## 三、核心模型与框架整理

### 1. One-Caption-Model：结构化打标模型

图片中显示，One-Caption-Model 是基于 Qwen2-VL 微调的结构化打标模型，核心流程为：

```text
读取批量图片 -> 调用 Qwen2-VL -> 生成 caption / JSON 结构化标签
```

该模型位于 Public-VLM 与 Custom-VLM 之间。相比通用 Public-VLM，它经过 fine-tuning，更适合输出稳定的固定标签；相比 GDINO 路线，它不依赖目标检测框的初步筛查，可以直接对整张驾驶场景图像输出结构化结果。

图片中可识别的标签属性包括：

- `scene_classification`：场景分类
- `illumination_classification`：光照分类
- `time_classification`：时间分类
- `weather_classification`：天气分类
- `Parkingspot`：车位属性

图片中还出现了批量推理脚本的大致逻辑：

```text
run_caption_vlm()
  -> 设置 current_time / task_name
  -> 设置 batch_size、debug、visualize
  -> 指定 image_dir 和 output_dir
  -> 调用 demo/qwen2vl_vlm.py 一类脚本
  -> submit_task 提交任务
```

可提炼为实习内容：

- 梳理基于 Qwen2-VL 的结构化打标模型流程。
- 理解批量图片输入、Prompt 调用、模型推理、JSON 标签输出的链路。
- 关注结构化输出在自动化标注、数据筛选和下游评估中的价值。

### 2. GDINO / Grounding DINO：开放词汇目标检测

图片中将 `dino / gdino` 定位为开放词汇目标检测框架，主要用于文搜图和目标定位。

它的特点是根据文本目标在图像中定位对应对象，并输出检测框、置信度和图像尺寸等结果。适合处理“有没有某类目标”“目标数量是否足够”“目标框在哪里”这类问题。

图片中可识别的支持类别包括：

- traffic sign
- traffic light
- vehicle
- person
- cone
- tripod
- loader
- bus

可提炼为实习内容：

- 理解 Grounding DINO 在开放词汇检测和文本驱动目标召回中的作用。
- 梳理检测框、置信度、图像尺寸等输出结构。
- 分析其在锥桶、水马、柱子、交通标识、车辆、行人等目标挖掘任务中的适用性。

### 3. GDINO + VLM：两阶段目标挖掘流程

图片中的流程图体现了一个“专用模型优先、通用模型兜底”的目标挖掘 pipeline。

整理后的流程如下：

```text
图片 / 视频抽帧
  -> 判断挖掘目标是否在支持标签中
  -> 如果目标在 GDINO 支持类别内，选择 GDINO 模型检测
  -> GDINO 输出检测框和结果文件
  -> 判断目标是否能被 GDINO 精确支持
  -> 如果需要细粒度属性，裁剪 bbox 内目标图
  -> 对裁剪图调用 Custom-VLM，使用固定 prompt 识别属性
  -> 如果目标不在专用支持范围内，调用 Public-VLM 做开放域描述
  -> 后处理提取最终挖掘目标和标签
```

这个流程体现的设计逻辑：

- 能用 GDINO / Custom-VLM 解决的任务优先用专用模型，提高效率和准确率。
- GDINO 负责目标定位，Custom-VLM 负责 bbox 内细粒度属性识别。
- Public-VLM 作为兜底，覆盖长尾、开放域或未被支持类别覆盖的场景。
- 最终通过后处理把模型输出转换成可入库、可检索、可用于数据闭环的标签。

## 四、mining-system 工程链路整理

### 1. tagger 与模型映射关系

图片中提到：没有一张集中式“注册表”直接说明某个 tagger 用哪个模型，映射关系分散在多个文件中，需要沿链路排查。

整理后的映射链路：

```text
config.yaml
  -> 定义本次任务跑哪些 tagger 和版本

 taggers/<name>/*.yaml
  -> 通过 use_* 字段说明使用哪类模型

base_tagger.py
  -> 提供 dino_inference / qwen2_inference / one_caption_model_inference 等推理接口

processer.py
  -> load_model，加载实际模型 checkpoint / wrapper
```

这部分可以体现的能力：

- 能从工程配置层面理解 tagger 与模型的关系。
- 能沿着配置文件、tagger 文件、base_tagger 推理接口和 worker 追踪实际模型调用。
- 能为团队交接、任务排查和模型替换提供文档化支持。

### 2. DINO 推理调用链

图片中给出了从 `tagging_main.py` 到 DINO 模型真正 forward 的完整链路。整理如下：

```text
tagging_main.py
  -> TaskFactory.get_task('clip')(task_info); task.run()

 task_manager/task_manager.py
  -> TaskFactory.get_task -> ClipTaggingTask

 task_manager/tagging_task.py
  -> TaggingTask.run()
  -> run_batch()
  -> run_vehicle_day_tagger()
  -> single_run() / multi_run()
  -> run_one_task()

base_tagger.py
  -> BaseTagger.run()
  -> self.process(...)

objs_by_dino_tagger_v011.py
  -> process(...)
  -> self.dino_inference(...)

base_tagger.py
  -> dino_inference
  -> RabbitCli().batch_inference('dino', 'v6.0', ...)

utils/model_processer.py
  -> push('dino', msg) 进入 RabbitMQ 队列

processer.py
  -> dino worker
  -> GdDino.batch_inference(imgs)
  -> 模型真正 forward
```

核心理解：

- `tagger` 插件是在自己的 `process()` 方法里调用推理接口。
- `tagging_main` 经过多层任务调度后才进入具体模型推理。
- DINO 推理通过 RabbitMQ 队列进入对应 worker，真正的模型 forward 发生在 worker 内。
- 这类链路梳理适合写成“复杂系统链路梳理、模型调用排查、工程交接文档沉淀”。

## 五、模型类型与输出格式

图片中提到 `mining-system` 中有多类模型，覆盖结构化打标、目标检测、视觉语言模型等方向。OCR 能较明确识别出的模型类型如下。

### 1. dino / Grounding DINO

用途：

- 输出检测框和置信度。
- 判断目标是否存在、数量是否满足条件。
- 适合锥桶、水马、柱子、交通参与者等明确目标的挖掘。

典型输出形式：

```text
{ts: {class_name: {boxes: [...], scores: [...]}}, img_width, img_height}
```

### 2. model / qwen2

用途：

- VLM 自由文本描述或问答。
- tagger 需要自己写 prompt，并自己解析模型生成文本。

图片中可识别的 prompt 示例方向：

```text
请描述图中路面上除车以外的物体，请列出它们的类型和颜色、形状。
```

适合任务：

- 判断图中是什么物体。
- 判断目标颜色、形状和语义属性。
- 判断是否属于某类复杂场景。

### 3. qwen3 / qwen3_imgs

用途：

- Qwen3-VL 单图理解。
- `qwen3_imgs` 支持双图输入，例如参考图 + 目标图的验证推理。

### 4. one_caption_model

用途：

- 输出固定 label 集合的结构化 JSON。
- 适合场景、光照、天气、时间、车位属性等固定分类任务。

与 qwen2 自由文本输出的区别：

- qwen2 输出自由文本，需要后处理解析。
- one_caption_model 是微调过的结构化模型，直接输出固定标签，更适合自动化入库和评估。

### 5. 专用检测 / 两阶段属性模型

图片中还出现了：

- `water_horse_dino`：专门检测“注水水马”等目标。
- `tsr_gdino + tsr_qwen2`：交通场景检测 + 逐框属性标注，两阶段输出检测框和属性。
